# Dots app ↔ Hermes gateway protocol

English translation of [protocole-gateway.md](protocole-gateway.md) (French original).

Version 1, 2 November 2026.

## Architecture

```
Pixel (Hermes app) ──wss://<domain>/dots/ws──▶ Caddy (Let's Encrypt TLS, :443)
                                                  │ reverse proxy
                                                  ▼
                                  127.0.0.1:8787  "dots" plugin (aiohttp)
                                                  │ BasePlatformAdapter
                                                  ▼
                                  Hermes gateway 0.22.2 (hermes-gateway.service)
```

- The **plugin** lives in `~/.hermes/plugins/dots/` (`plugin.yaml`, `__init__.py`, `adapter.py`). It has
  no impact on Hermes's own code and survives a `hermes update`.
- The WebSocket server listens **on 127.0.0.1 only**. Only Caddy is exposed, and it handles HTTPS.
- Configuration happens through `DOTS_*` variables in `~/.hermes/.env`:

| Variable | Role |
|---|---|
| `DOTS_TOKEN` | Pairing token (32 random bytes), to be entered in the app |
| `DOTS_BIND` | Listen address, `127.0.0.1:8787` by default |
| `DOTS_ALLOWED_USERS` | `owner` |
| `DOTS_HOME_CHANNEL` | `owner` (target of proactive messages and cron jobs) |
| `DOTS_WEB_ORIGINS` | Allowed web app origins, comma-separated. `install.sh` puts the main web app origin there (`https://dots-hermes.vercel.app` unless configured otherwise, see its `--default-web-origin`). Empty: no browser accepted |

## Connecting

- URL: `wss://<domain>/dots/ws`. Authentication goes through the `Authorization: Bearer <DOTS_TOKEN>`
  header. An invalid token receives an HTTP 401 before the upgrade.
- Browser (web app): a web token of its own, offered as a subprotocol (`dots.v1`,
  `dots.token.<token>`), `Origin` checked against `DOTS_WEB_ORIGINS`. See [web-pairing.md](web-pairing.md).
- There is only **one conversation**: `chat_id = user_id = "owner"`.
- A WebSocket ping is sent every 30 s. The app reconnects with a backoff of 1, 2, 5, 10 then 30 s.

## Frames

Every frame is JSON with a `type` field. Message ids are generated by the server. `seq` is an
ever-growing counter of the conversation, used to catch up on missed messages.

### App → gateway

| `type` | Fields | Effect |
|---|---|---|
| `hello` | `last_seq`, `foreground`, `push_token` (optional), `lang` (optional, `en` / `fr`) | `last_seq = 0`: the most recent page (120 events); otherwise whatever was missed (600 max, beyond that the recent page with `reset`); declares presence, the FCM token and the phone's language (texts written by the plugin: push, tool labels, sub-dot prompts; English by default, remembered in `~/.hermes/platforms/dots/app_language`) |
| `history_page` | `before_seq`, `limit` (200 max) | Older history page (scrolling up) |
| `message` | `client_id`, `text` | The user's message, forwarded to `handle_message` |
| `reaction` | `message_id`, `emoji` (`null` = remove) | Emitted to the hooks via the reaction handler |
| `approval` | `approval_id`, `choice` (`once`, `session`, `always`, `deny`) | `resolve_gateway_approval` |
| `clarify` | `clarify_id`, `response` | `resolve_gateway_clarify` |
| `voice` | `client_id`, `mime` (`audio/mp4`), `duration_ms`, `waveform[]` (0..1), `audio` (base64, 6 MB max) | Voice note: stored in `~/.hermes/platforms/dots/voice/`, forwarded to Hermes as `MessageType.VOICE` |
| `audio_get` | `id` | Requests the audio of a voice note from the history |
| `file` | `client_id`, `name`, `mime`, `caption`, `data` (base64, 20 MB max) | Attachment: copied for the history, cached by `cache_media_bytes` and forwarded to Hermes (PHOTO, VIDEO, AUDIO or DOCUMENT) |
| `file_get` | `id` | Requests an attachment from the history |
| `screen_watch` | `on`, `takeover` | Opens/closes the live screen stream; `takeover` speeds the stream up during a takeover |
| `screen_input` | `action` (`click`, `scroll`, `type`, `key`), `x`, `y` (fractions of the image), `dy`, `text`, `key` | Gesture replayed on the agent's page via CDP (`Input.*`) |
| `takeover_done` | `id`, `note` | Hands control back to the agent (unblocks `browser_request_takeover`) |
| `activity_get` | — | Requests the Activity view |
| `usage_get` | `from`, `to` (epoch ms) | Requests hourly usage over this window (40 days at most) |
| `cron_action` | `id`, `action` (`pause`, `resume`, `run`) | Drives a cron job, returns the Activity view |
| `stop` | — | Interrupts the current turn (`/stop`, not written to the conversation) |
| `presence` | `foreground` | The app goes to the foreground / background (drives push) |
| `push_token` | `token` | The device's new FCM token (4 kept at most, in `push_tokens.json`); ignored from a browser |
| `web_token_create` | `ref`, `origin`, `label` | Phone only: creates the token of a browser paired by QR ([web-pairing.md](web-pairing.md)) |
| `web_sessions_get` | — | Phone only: lists the web sessions |
| `web_revoke` | `id` (optional from a browser: its own session) | Revokes a web session and closes its sockets (code 4401) |

### Gateway → app

| `type` | Fields | Origin on the adapter side |
|---|---|---|
| `welcome` | `agent` (name), `seq`, `history[]`, `reset`, `has_more` | Reply to `hello`; `reset`: the app replaces its thread instead of extending it |
| `history_page` | `before_seq`, `events[]`, `has_more` | Reply to `history_page` |
| `ack` | `client_id`, `id`, `seq`, `ts` | User message stored |
| `read` | `id` | `on_processing_start` |
| `activity` | `state`: `thinking`, `typing` or `idle` | `send_typing` / `stop_typing` / streaming |
| `message` | `id`, `seq`, `ts`, `text`, `final`, `turn` | `send` (including proactive and cron messages); `turn` = id of the user message being answered, `null` outside a turn |
| `edit` | `id`, `text`, `final` | `edit_message` (streaming reply) |
| `reaction` | `message_id`, `emoji` | `_add_reaction` / `_remove_reaction` (raised by the processing) |
| `approval` | `approval_id`, `seq`, `title`, `command`, `description`, `actions[]` | `_send_exec_approval_prompt` |
| `approval_resolved` | `approval_id`, `choice` | After resolution |
| `clarify` | `clarify_id`, `seq`, `question`, `choices[]` | `send_clarify` |
| `transcript` | `id` (voice note), `text` | Hermes's STT echo (`🎙️ "…"`), intercepted by `send` and attached to the voice note |
| `audio` | `id`, `mime`, `data` (base64) or `error` | Reply to `audio_get` |
| `file_data` | `id`, `mime`, `name`, `data` (base64) or `error` | Reply to `file_get` |
| `screen_frame` | `data` (base64 JPEG), `url`, `title`, `width`, `height`, `live`, `ts` | Screen image: one thumbnail after each `browser_*` tool, ~3 frames/s while an app is watching |
| `screen_idle` | — | No browser open during the stream |
| `activity_snapshot` | `crons[]`, `turn`, `state`, `browser` | Reply to `activity_get` / `cron_action` |
| `usage` | `from`, `to`, `hours[]` = `[UTC hour since the epoch, tokens, messages]` | Reply to `usage_get`; only active hours appear in it |
| `tool` | `id` (tool_call_id), `turn`, `name`, `kind`, `label`, `detail`, `state` (`running`), `ts` | Plugin hook `pre_tool_call`, filtered on `HERMES_SESSION_PLATFORM == "dots"` |
| `tool_update` | `id`, `state` (`done` / `error`), `duration_ms` | Hook `post_tool_call`; the history keeps the final state in the `tool` event |
| `web_token` | `ref`, `token`, `id` or `error` (`origin_not_allowed`), `origin` | Reply to `web_token_create` |
| `web_sessions` | `sessions[]` = `{id, label, origin, created_at, last_seen}` | Reply to `web_sessions_get` / `web_revoke` |
| `error` | `code`, `message` | Invalid frame, refused token, `forbidden` (phone-only frame)… |

## Offline messages

The adapter keeps the whole conversation (messages, cards, tools, resolutions) in a SQLite database,
`~/.hermes/platforms/dots/history.db`: an insert or an update writes a single row, and the app walks
the thread page by page. The older `history.jsonl` was imported once, then kept as
`history.jsonl.migrated`. While the app is disconnected, `send` still succeeds: the message is
stored, then delivered at the next `hello`. The agent can therefore write first (cron, proactive
research) without anything being lost.

## Mapping to the interface

| Interface (phase 1) | Protocol |
|---|---|
| "Thinking… / Typing…" status and mascot mood | `activity` |
| Receipts "Sending… → Sent → Read" | local send → `ack` → `read` |
| Approval card (Approve / Deny) | `approval` / `approval_resolved`; Approve = `once`, Deny = `deny` |
| Emoji reactions | `reaction` (both ways) |
| Task card | No native equivalent in Hermes 0.22: kept available for a later release |
| Tool over-messages (capsule above the reply, expandable into a trail) | `tool` / `tool_update`, grouped by `turn` and placed before the agent reply that follows them |
| Push notification | FCM, see below |

## Tools and skills

Hermes does not expose tool calls to platform adapters, except as text lines (`tool_progress`). The
plugin therefore subscribes to the global `pre_tool_call` / `post_tool_call` hooks, which give the
tool's name, its arguments and a `tool_call_id`. It keeps only the calls of Dots turns
(`HERMES_SESSION_PLATFORM` context variable), translates the name into a label (in the app's
language, see `hello`) and into an icon family (`kind`: `skill`, `terminal`, `web`, `memory`…), and
computes the detail with `agent.display.build_tool_preview`. Reading a skill, for instance, arrives
as `skill_view` with the skill's name as the detail.

The text progress lines are muted for this platform
(`display.platforms.dots.tool_progress: off` in `config.yaml`): without it, every call would become
a "⏰ Scheduling list" bubble.

## Push notifications (FCM)

- Firebase project `hermes-perso-513222`, Android app `app.dotshermes` (`app/google-services.json`).
- Service account `dots-fcm-sender@hermes-perso-513222.iam.gserviceaccount.com`, role
  `roles/firebasecloudmessaging.admin` only. Key on the server in
  `~/.hermes/platforms/dots/fcm-service-account.json` (mode 600), path overridable with
  `DOTS_FCM_CREDENTIALS`.
- The plugin pushes when no app is connected **or** it declared `foreground: false`: for every agent
  `message`, every `approval` and every `clarify`.
- Data-only messages, high priority (`kind`, `id`, `title`, `body`): the app composes its own
  conversation notification (MessagingStyle) with a quick reply. The reply goes through the open
  socket if the app is running, otherwise through a flash connection (`hello` without catch-up,
  `message`, `ack`).
- Tokens rejected by FCM (`UNREGISTERED`) are removed automatically.

## Voice notes

- The app records mono 16 kHz AAC at 32 kb/s (MP4 container), with a 40-bar envelope to draw the
  waveform without downloading the audio.
- The plugin creates a `MessageEvent` of type `VOICE` whose `media_urls` points at the file: it is
  Hermes's STT pipeline that transcribes it, before the agent reads the message.
- The STT is **local** (faster-whisper, the `stt-whisper` extra installed with
  `hermes pm install --extra stt-whisper`, the `base` model, `stt.language: fr`). No audio leaves
  the server.
- Hermes echoes the transcription back (`🎙️ "…"`); the plugin intercepts it and shows it under the
  voice bubble instead of turning it into a message.
- The history keeps the waveform, the duration and the transcription; the app downloads the audio
  (`audio_get`) only when listening from another device or after a reinstall.

## Several apps connected

The plugin accepts several WebSockets at the same time (phone, quick reply from a notification,
another device, browser): conversation events go to all of them, including the owner's messages (to
all but the one that wrote them, which already has its `ack`), replies to requests (`welcome`,
`audio`, `file_data`, `activity_snapshot`) to the one that asked. Each declares its presence; push
is sent only if none is in the foreground.

## Attachments

- **App → Hermes**: the plugin keeps a copy in `~/.hermes/platforms/dots/files/` (to show it again)
  and hands the file to Hermes with `cache_media_bytes`, like the official adapters: an image goes
  as `PHOTO` (the `vision_analyze` tool), a PDF or a text as `DOCUMENT`. The text typed before
  sending serves as the caption.
- **Hermes → app**: `send_image_file`, `send_document`, `send_video`, `send_voice` (speech
  synthesis, shown as a voice note) and `send_image` (remote URL downloaded) produce a `message`
  event of `kind: file` or `voice`.

## The browser screen

The plugin goes through the CDP access that Hermes reserves for plugins
(`SUPERVISOR_REGISTRY.capture(task_id)`), with the `task_id` of the Dots turn's `browser_*` tools.
The supervisor is attached to Chromium's first tab, often blank: the plugin looks for the page
actually being viewed (`Target.getTargets`, last web page) and attaches to it. The images are
`Page.captureScreenshot` JPEGs reduced to 60%; nothing is captured while nobody is watching, apart
from a thumbnail after each action.

## Activity view

- Cron jobs, read and driven with Hermes's cron API (`list_jobs`, `pause_job`, `resume_job`,
  `trigger_job`).
- Current turn, its tools and the "Stop" button (`stop`).
- Latest exchanges, rebuilt by the app from the messages and the tools (`turn`).
- Usage, at the top: a GitHub-style month grid (`usage_get`), darker on the most active days.
  - **Tokens**: everything the agent spends, all Hermes sessions combined (cron jobs included).
    `state.db` only keeps a total per session: the plugin reads those totals every 5 minutes (and on
    every `usage_get` touching today) and records their increase in the current hour
    (`platforms/dots/usage.db`). A session never seen before — the whole past, on first launch — is
    spread over the hours of its messages: an estimate for history, then exact readings.
  - **Messages**: those of the app's history (yours and the dots'), all conversations combined.
  - The gateway counts by UTC hour; the app groups by day in the phone's time zone.

## Browser takeover

Hermes closes its browser at the end of every turn. A takeover therefore only makes sense if the
agent waits during its turn. The plugin gives it a tool for that, `browser_request_takeover(reason)`,
declared in the `dots` tool set (Hermes adds it automatically to this platform's tools):

1. The agent leaves the browser on the page that asks for a human (login, 2FA code, captcha…) and
   calls the tool. The call blocks its turn (15 min at most), so the browser stays open.
2. The plugin publishes a `kind: takeover` message (a "Needs you on its browser" card) and a push
   notification.
3. The "Take over" button opens the live screen in steering mode: tap = click, drag = scroll, a text
   field = `Input.insertText`, and the Enter, Backspace, Tab and Escape keys.
4. "Hand back" sends `takeover_done`: the tool answers the agent, which resumes with the page in the
   state left by the user.

Whatever the user types goes straight to the page. Nothing goes through the conversation, the
history or the model.

## Approval notifications

For an approval request, the app shows a separate notification, with "Deny" and "Approve" buttons.
The decision goes through the app's socket if it is connected, otherwise through a flash connection
that waits for `approval_resolved`. If the request is settled elsewhere (in the app, on another
device), the notification disappears.

## Several agents

One plugin serves **one** agent: the Hermes profile it is installed in (`HERMES_HOME`). For several
independent agents, each has its profile, hence its gateway, its token, its port and its route
behind Caddy. The app keeps one connection per paired agent; nothing is shared between two
connections, and isolation (memory, tools, skills, credentials) is that of the Hermes profiles.

| Field | Where | Role |
|---|---|---|
| `agent_id` | `welcome` | Stable id of the agent: `DOTS_AGENT_ID`, otherwise derived from the profile's folder (16 hex characters) |
| `agent` | `welcome` | Default display name: `DOTS_AGENT_NAME`, otherwise the profile's name (`~/.hermes/profiles/<name>`), otherwise `Hermes` |
| `agent` | push data | `agent_id` of the notifying agent: the app attaches the notification, its quick reply and its approval buttons to it |
| `agent_id` | `GET /dots/health` | Same id, to check which profile answers on a port |

Compatibility: these fields are additions. An older app ignores them; a recent app facing a plugin
older than 1.2 puts everything in the single agent. A notification without `agent`, or whose agent
is unknown, is only shown if the app can attribute it unambiguously (see `routePush` in
`AgentStore.kt`): a quick reply must never go to another agent.

## Sub-dots

The main dot is the `owner` conversation. Each sub-dot has its own conversation, `dot-<id>`, hence
its own Hermes session: Hermes isolates private sessions by `chat_id`, and the context is not shared
(checked: a code word entrusted to one dot remains unknown to the others). Tools, memory and skills
stay shared.

| Kind | Role | End of life |
|---|---|---|
| `temporary` | A mission; without a name it takes the first words of its mission | Closed once the mission is done (the agent says so) |
| `permanent` | A lasting specialist with its own name, mascot and colour | Deleted only on request |

- **Registry**: `~/.hermes/platforms/dots/dots.json` (`id`, `name`, `kind`, `mission`, `species`,
  `palette`, `accessory`, `created_at`). It lives on the server, so it is common to every device.
- **Identity**: with each message, the mission or the specialization goes into
  `MessageEvent.channel_prompt`, Hermes's per-conversation prompt. It is applied on every call and
  never written to the transcript: editing a dot changes its behaviour from the very next message.
- **History**: a single table, with a `chat` column. Pages (`history_page`) are requested per
  conversation. Closing a dot deletes its rows and interrupts its turn if it was working.
- **Routing**: messages from the app carry `chat` (`owner` by default), and the server events do
  too. Activity is tracked per conversation (`activity` + `chat`, `welcome.activities`). Tools find
  their conversation back through `HERMES_SESSION_CHAT_ID`, and approvals through their
  `session_key`. Crons and unknown targets land in the main dot.

| App → gateway | Fields |
|---|---|
| `dot_create` | `ref`, `dot` {name, kind, mission, species, palette, accessory} |
| `dot_update` | `id`, `dot` (same fields) |
| `dot_delete` | `id` |

| Gateway → app | Fields |
|---|---|
| `dots` | `dots[]` (with `last_ts`): broadcast after every change, and included in `welcome` |
| `dot_created` | `id`, `ref`: the app that created it opens its conversation |
| `dot_deleted` | `id` |

Push: `chat` and `title` (the sub-dot's name; empty for the main one) in the data. All notifications
share a thread, each dot under its name. "Reply" and opening the app lead to the conversation of the
last message.

## Group room

From the "+" button, you invite sub-dots into the conversation being viewed. Every message typed in
this room is debated: each guest speaks in turn for 2 rounds (3 at most), seeing what the others
just said, then the conversation's dot wraps up.

- **Sessions**: a guest speaks in its own Hermes session, `<dot id>~<conversation>` (for instance
  `dot-ab12~owner`). Its private conversation stays untouched, and it remembers this room's previous
  debates. The plugin only sends it what it has not read yet (40 events at most), without its own
  replies.
- **Prompts**: the guest receives in `channel_prompt` its identity, its specialty, the host and the
  other participants, with the instruction to answer in a few sentences. The dot that wraps up
  receives the debate's transcript and its usual prompt.
- **Thread**: everything a guest says (messages, tools, approvals, takeovers) is filed in the room's
  conversation, with `speaker` (the sub-dot's id) and `speaker_name`. All replies carry the `turn`
  of the user's message.
- **Activity**: `activity` carries `speaker` while a guest has the floor. The room stays occupied
  from one guest to the next, then goes back to `idle` after the wrap-up. `welcome.speakers` gives
  the current speaker on reconnection.
- **Stop**: `stop` on the conversation stops the whole debate and the current speaker's turn. A new
  message in the conversation replaces the ongoing debate.
- **Push**: the guests' replies do not notify; only the wrap-up notifies. Approvals and questions
  always notify, with the guest's name.

| App → gateway | Fields |
|---|---|
| `message` | `room` (ids of the invited sub-dots, 4 at most, in speaking order), `rounds` (optional, 1 to 3, 2 by default) |

| Gateway → app | Fields |
|---|---|
| `message`, `tool`, `approval`, `clarify` | `speaker`, `speaker_name` when a guest speaks |
| `activity` | `speaker` when a guest has the floor |
| `welcome` | `speakers`: conversation → current speaker |
